## 2. Cosa è cambiato

### Content-Security-Policy (`lib/security-headers.mjs`, usata da `next.config.mjs`)
Produzione:
```
default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-src 'none';
worker-src 'self'; manifest-src 'self'; media-src 'self'; object-src 'none'; base-uri 'self';
form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests
```
Cosa ho dovuto consentire e perché:
- `'unsafe-inline'` per gli script: Next.js inserisce piccoli script inline in ogni pagina. L'alternativa (nonce per richiesta) renderebbe dinamiche tutte le ~1.700 pagine oggi prerenderizzate: più lente su iPhone e senza le copie statiche su cui si appoggia l'offline. Il rischio residuo è contenuto: nessun contenuto utente viene mai inserito come HTML (§5 della tabella route) e nessun'altra origine può caricare script.
- `'unsafe-inline'` per gli stili: attributi `style` di React e Next.
- `data:` e `blob:` per le immagini: icone inline e anteprime generate nel browser.
- Font: solo `'self'` (EB Garamond e Source Sans 3 sono serviti dal sito tramite `next/font`, nessuna chiamata a Google Fonts).
- `connect-src 'self'`: le statistiche passano da `/api/analytics`; PostHog è chiamato solo dal server.
- Solo se servono: `https://challenges.cloudflare.com` (Turnstile, quando le due chiavi sono impostate); `https://vercel.live` e affini (barra Vercel) **solo nelle anteprime**; `'unsafe-eval'` solo in sviluppo locale.
- Interruttore di emergenza: `GRIMORIO_CSP=report-only` su Vercel (poi ridistribuire) manda la stessa policy come `Content-Security-Policy-Report-Only`.
- Aggiunta anche `Cross-Origin-Opener-Policy: same-origin`.

Prova Report-Only: build con `GRIMORIO_CSP=report-only` e tutte le 26 prove nel browser. Unico messaggio: «upgrade-insecure-requests ignorata in modalità report-only» (normale, ora omessa in quella modalità). **Nessuna violazione** su ricerca, segnalazioni, offline, admin, schede. Poi attivata: 27 prove verdi, compresa la nuova prova di sicurezza.

### Sessione admin (`lib/admin-auth.ts`)
- Durata 7 giorni (era 30). Token `v3.<scadenza>.<id casuale>.<firma HMAC>`, confronto a tempo costante.
- Tabella `grimorio_admin_sessions` (id, expires_at), creata al primo uso (migrazione additiva). `isAdmin` controlla firma **e** riga nel database; senza database l'area resta chiusa.
- Logout: cancella la riga, quindi un cookie copiato smette subito di funzionare.
- Cookie `__Host-grimorio_admin`, httpOnly, secure, path `/`, `sameSite=strict` in produzione.
- Per non rompere il flusso con `strict` (link dall'email delle segnalazioni): le pagine admin senza sessione mostrano il login **sul posto** e, dopo l'accesso, la stessa pagina si ricarica con i dati.
- Effetto una tantum: dopo l'unione serve un nuovo accesso (i cookie della versione precedente non valgono più).
- Il login usa sempre `ADMIN_PASSCODE`.

### Limite tentativi (`lib/admin-login-limit.ts`)
- Per dispositivo: 5 errori in 15 minuti. Globale: 100 errori in un'ora da qualsiasi indirizzo.
- Conteggio nel database (`grimorio_admin_login_failures`, solo hash), quindi sopravvive ai riavvii delle funzioni.
- Indirizzo da `x-real-ip` (Vercel lo imposta e sovrascrive `x-forwarded-for`): un client non può cambiarlo mandando intestazioni inventate. Test dedicato in `tests/admin-access.cjs`.

## 3. Verifica in due passaggi (proposta, NON attivata)
Soluzione più semplice e sicura: **codice TOTP a 6 cifre** (Google Authenticator, 1Password, Authy…), nessun servizio esterno, nessun costo.
1. Daniele genera un segreto TOTP: lo creo io in una pagina admin protetta, che mostra un QR una sola volta.
2. Lo salva nell'app autenticatrice e mi conferma un codice.
3. Su Vercel, in Production, aggiunge `ADMIN_TOTP_SECRET` (tipo Sensitive), poi ridistribuisce.
4. Il login chiede passcode + codice (finestra ±30 s, codice non riutilizzabile, stesso limite tentativi).
5. Recupero: 5 codici di emergenza monouso, mostrati una volta e salvati come hash.
Rischio: se si perde il telefono senza codici di emergenza, l'accesso si ripristina togliendo la variabile da Vercel.

## 5. Route e azioni server

| Percorso | Metodo | Chi può chiamarla | Cosa scrive |
|---|---|---|---|
| `/api/segnalazioni` | GET | Tutti | Niente (gettone firmato con l'ora) |
| `/api/segnalazioni` | POST | Tutti, solo dal sito (Origin = host) | Una segnalazione + hash per il limite. Antispam: trappola, 3 s, 5/h-20/g per dispositivo, 60/h globale, 8 KB max |
| `/api/analytics` | GET | Tutti | Niente |
| `/api/analytics` | POST | Tutti, solo dal sito; eventi solo con consenso e ID firmato | Scelta di consenso (cookie); eventi statistici (admin e bot esclusi) |
| `/api/analytics/maintenance` | GET | Solo cron Vercel con `CRON_SECRET` (401 altrimenti) | Cancella eventi > 90 giorni, esporta a PostHog |
| `/ricerca-indice.json` | GET | Tutti | Niente |
| `/sw.js` | GET | Tutti | Niente |
| `loginAction` | azione | Tutti (limitata) | Tentativi falliti (hash), sessione admin |
| `logoutAction` | azione | Tutti | Cancella la propria sessione |
| `create/update/deleteSpellAction` | azione | Solo admin | Incantesimi |
| `create/update/deleteMonsterAction` | azione | Solo admin | Mostri, dettagli, habitat |
| `setContentEditionAction` | azione | Solo admin | Etichetta edizione |
| `feedbackState/Note/DeleteAction` | azione | Solo admin | Stato, nota, eliminazione segnalazioni |

- Nessuna scrittura senza login, tranne segnalazioni e statistiche (con antispam e consenso).
- CSRF: le azioni server di Next controllano che `Origin` coincida con l'host; in più il cookie admin è `sameSite=strict`. Le due API POST controllano l'origine.
- Input: tutte le azioni puliscono e validano (`clean`, controlli di tipo, id uuid per le segnalazioni, stati da elenco chiuso).
- HTML: `dangerouslySetInnerHTML` non è usato da nessuna parte (`components/html-text.tsx` ricostruisce il markup consentito); i testi utente sono sempre mostrati come testo.
- SQL: solo query parametrizzate (`$1`) o Drizzle. L'unico frammento interpolato (`lib/analytics.ts`, `where`) è una costante del codice.

## 6. Segreti e variabili

## 10. Repository privato e pulizia della cronologia — guida (NON eseguita)
Da fare insieme dopo un «procedi».

**A. Backup (prima di tutto)**
```bash
git clone --mirror https://github.com/Dandi83/grimorioapp2024.git grimorioapp2024-backup.git
tar czf grimorioapp2024-backup-$(date +%F).tgz grimorioapp2024-backup.git
```
Conservare il file fuori dal computer (es. Google Drive).

**B. Rendere privato** — GitHub → repository → Settings → General → Danger Zone → «Change visibility» → Private.
Controlli dopo: Vercel continua a distribuire (l'app GitHub di Vercel ha già accesso); Codex/Claude e le Actions continuano a funzionare.

**C. Pulire la cronologia (solo se si vuole togliere i vecchi `.env`)**
```bash
pip install git-filter-repo
git clone --mirror https://github.com/Dandi83/grimorioapp2024.git pulizia.git
cd pulizia.git
git filter-repo --invert-paths --path backend/.env --path frontend/.env
git push --force --mirror origin
```
Effetti: cambiano gli identificativi di tutti i commit; le PR aperte vanno ricreate o ribasate; chi ha una copia locale deve riclonare. Poiché quei file non contengono password, la pulizia è facoltativa: la privatizzazione basta.

**D. Rotazioni consigliate** (in ogni caso, dopo B): `ADMIN_PASSCODE`, password Neon, `CRON_SECRET`.
